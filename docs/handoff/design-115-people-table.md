Written by a build agent, 29-10-2026; revised after the reviews of 28-10 and 29-10 (the lead's three HIGH, a reviewer's four MEDIUM and four LOW), again after the second reader's plain-words read at 7ec7170, and again after a reviewer's read at 0a57bf17 (one HIGH, five MEDIUMs). **There is no VIP column in this release** (see "No VIP column"). **Not built.** The table needs changes to `schema.sql` and `store.py` (and a new route in `server.py`, a new `changes.py` path for the Excel and share carry). None of these is approved in #115, so this note stops at the design. It needs the Head's approval to move to a Full-tier item, and it builds **after #126** (#45 adds no schema step, so it does not hold this up; see Migration).

## What #115 asks for (the owner, 28-10-2026)
A small first version: a `people` table with name, email, organisation, role and aliases, plus a Needs details flag for a person added without details. Filled by Excel or CSV paste. The Microsoft 365 address-book pick is left for later. Owners stay free text in v0.5, with an optional link to a person. #116 (people from mail headers) follows.

## Table (creaite's style)
```
people(
  id          TEXT PRIMARY KEY  -- P-001, P-002 ... (own counter, never reused)
  name        TEXT NOT NULL CHECK length(trim(name)) > 0
  email       TEXT            -- stored trimmed and lower-cased; unique when not null
  organisation TEXT
  role        TEXT
  label       TEXT            -- optional short tag shown after the name, e.g. 'Harbour team'; display only
  aliases     TEXT            -- ";"-separated, like workstreams.aliases
  kind        TEXT NOT NULL DEFAULT 'person' CHECK IN ('person','group')
  needs_details INTEGER NOT NULL DEFAULT 0 CHECK IN (0,1)
  archived    INTEGER NOT NULL DEFAULT 0
  source      TEXT NOT NULL
  updated_at  TEXT NOT NULL DEFAULT (datetime('now'))
)
```
There is no VIP column and no private mark of any kind on this table (see "No VIP column"). People belong to the portfolio, not one project, so there is no project column. `email` has a unique index on the stored (lower-cased, trimmed) value, so `A@x.example` and `a@x.example` clash; a test proves it.

**Column rules (second read, MEDIUM 4).** One function in `store.py`, `clean_person_text`, applies to `name`, `organisation`, `role`, `label` and each alias before any write, import or Excel row: NFKC, trimmed, inner whitespace collapsed, every control character and every invisible or bidirectional-control character removed (zero-width, bidi marks and embedding/isolate controls, line and paragraph separators). Limits: name 1 to 100, organisation and role 0 to 100, label 0 to 30, an alias 1 to 100 and at most 10 aliases per person. An alias may not contain `;` (it is the separator); a `;` typed in an alias is refused with the plain-words message "An alias can't hold a semicolon. Add each alias on its own.". Import and paste are capped at 500 rows and 200 KB; over the cap nothing is read and the message says "That is more than 500 rows. Split it and import in parts.". The page escapes every name, alias and label when it draws them (text nodes, never `innerHTML`), and the People sheet passes every cell through `excel.to_cell` and `escape_text` (a name or organisation of `=cmd` or `=HYPERLINK(...)` is stored as text).

**ID shape (LOW 1, LOW 4; second read, MEDIUM 5).** `P-001` is a new shape, and it is not a work-item ID. `ID_PREFIX` is built for per-project work items (`<CODE>-A-001`), so `people` does **not** go in it: it gets its own constant `PERSON_PREFIX = 'P-'` and `next_person_id(con)` (the next number over all `people.id`, archived ones included, so a number is never reused; 999 people is the limit, refused in plain words). It does need entries in `KEYS`, `REQUIRED_NEW` and `ALLOWED`. The id GLOB check gets a second, person-only pattern (`P-[0-9][0-9][0-9]`) used only for `people.id` and `owner_id`; the work-item GLOB is not widened. `people` is not in `DELETED_ON_CANCEL`. History lines name a person by name, never by `P-001`. Tests: the ID scans (doclinks, the item-ID detail in the log) and `ITEM_REF` do not read `P-001`, `see P-001`, `P-001.` or `(P-001)` as a work item, and a work-item ID such as `ABC-A-001` is still read; `owner_id = 'ABC-A-001'` and `id = 'P-1'` are refused.

## Owners point at a row
`actions.owner`, `raid.owner`, `milestones.owner`, `workstreams.lead` and `decisions.made_by` are free text today (`TBC` default). Two options:

1. **Keep the text, add an optional `owner_id`** beside it (recommended; a reviewer agrees). The text stays the shown name, so reports, Excel and the existing demo data keep working.
2. Replace the text with a foreign key. Cleaner, but it changes every list, report and export at once. Not recommended in a small release.

### One resolver, in `store.py`
The writer, never the page, resolves a name. Every route that writes owner text goes through the same function: the page's edit, the Excel import (the owner cell), a teammate's changes file (`team` route), the board's drag and ask clark. A save whose text matches **exactly one** person sets `owner_id`; otherwise it keeps the text and sets no `owner_id`.

**Matching (LOW 3).** The normalisation key is NFKC, casefold, collapse whitespace, then `confusables.skeleton` (the repo's reading of text), so accents and look-alike letters are treated as the repo already treats them. Exact match on the key of the name or any alias; no fuzzy matching. `TBC` and blank map to no person. A text that matches two people (live ones; an archived one is not counted) sets **no** `owner_id` and the save says why in plain words (below): it never guesses. **Two real people may share a name** (two Sam Reeds in different teams). A name is not unique; an **email is** (one person per address). They are told apart on screen by their email, or by an optional short **label** shown after the name, for example "Sam Reed (Harbour team)". The label is one more column, `label TEXT` (at most 30 characters, plain text), used only for showing; it is not matched on. Everywhere a person is listed or picked (the People list, the owner type-ahead, the merge and rename questions) the name is followed by the label, or the email if there is no label, whenever two live people have the same name. A name that matches two people sets no link and says why (see the messages). An **alias** may be on two people for the same reason, but adding an alias that another person already has shows a warning first (see "Alias clash") and the user chooses.

### A new name never creates a person by itself (MEDIUM 2)
Saving or typing a name that matches no one keeps the text and sets no `owner_id`. Nothing creates a people row as a side effect: not a save, not typing, and not an Excel import (an import can carry hundreds of distinct owner texts, and typos would become junk people). People are made in only three places:
- the People list's Add;
- the import box on the People list (rows pasted there are people rows, checked like any save);
- the owner box, when the user confirms a prompt: **"Add Sam Reed as a new person?"** with the replies **Add person** and **Keep the name only**. Add person creates the person with `needs_details = 1` and sets `owner_id`, in the same step as the save; Keep the name only changes nothing but the text. `TBC` and a blank owner never raise the prompt.

The People list also shows **Not on the people list yet**: the distinct owner texts that match no one, with a count each, and an **Add** beside each, so several can be added in one go. The Excel import of work items only ever sets `owner_id` for an existing person (name or alias match) and creates no one. Its plan (the screen shown before anything is saved) has these lines, each only when its count is above 0:
- "11 items now point at a person." (names that matched exactly one person)
- "2 owner names match more than one person and will be saved as typed: Sam (Sam Reed, Sam Reid)." 
- "3 owner names are not on the people list and will be saved as typed: Sam Rede, Jo Park, Li Wen."
- Under the last two lines, beside each name, a choice: **Same person as …** (a list of the live people), **Add as new person**, or **Keep the name only** (the default). **Same person as …** saves the spelling as an alias of that person and links the items, so "Sam Rede" is tied to Sam Reid and the next import matches it with no question. If the alias is already on another person, the alias-clash message below is shown.
- Then: "Nothing is saved until you press Import. Reply **Import** or **Cancel**." A name left on its default is saved as typed, exactly as today.

The **Needs details** flag clears in the same step when a save adds an email (LOW 4 of the first review), so it cannot go stale.

### Migration and backfill
Schema version 4, built on **the same runner as #126's version 2** (HIGH 2): one ordered `MIGRATIONS` table in `open_store`, `{2: …, 3: …, 4: …}`, walked from the file's version. The Head's ruling (29-10-2026, 06:34): **#83 (#126) sets version 2** (`documents.archived`, copy-first through `backup.make`), **#120 sets version 3** and **#115 is version 4**, the fourth entry in the table after 2 and 3. **The number is the next free step at merge: today #120 is 3, and this is 4 only if #120 merges first.** If #120 slips, #115 takes 3 and the idempotence test must not assume a step 3 exists: it runs the step on a file at the version just below its own number and on the same file twice (the tests below read the number from the table, not a literal 4). The build also corrects the stale `#115: 3` comment on main's `MIGRATIONS` line, so nobody reads it as a ruling. Anything else takes the next free number at its merge. The table refuses a gap, so the people step must not assume #120's step has run: it takes the number free at its merge, and if it lands in another order the number is read again then. #45 adds no schema step (checked on the #45 branch: no `MIGRATIONS` entry, no change to `schema.sql`, no version change; it only changes `store.py` code). The note adds **no `open_store` branch of its own**. The runner takes one safety copy before the first step that runs (not one per step), every step is idempotent and re-reads the version after `BEGIN IMMEDIATE`, and `check_copy` accepts any version from 1 to the current. Step 4, in one transaction: `CREATE TABLE IF NOT EXISTS people` and `CREATE TABLE IF NOT EXISTS people_steps` (the Undo record, see "Where people changes are made and undone") first, then `CREATE TABLE IF NOT EXISTS people_staged` (people changes waiting for the owner, see "People changes from someone else"), (the `label` column is part of the new table) five `ALTER TABLE … ADD COLUMN owner_id TEXT REFERENCES people(id)` (a column with a default of NULL is allowed in SQLite; the table exists before the columns point at it).

**Backfill (HIGH 3).** The migration creates no people and sets every `owner_id` to NULL. The existing owner text keeps working exactly as today. Linking happens later, when the owner has filled the People list: the list offers **Match existing items to people** (a button, one step, with a count shown first), which runs the same resolver over the owner text of every live row: exact match on the key, one match only, `TBC` to none, no fuzzy matching. It is deterministic, repeatable and Undoable. Tests: a version 1 file with data migrates through 2 and 3 to 4 (a `label` is accepted and stored, and `people_steps` and `people_staged` exist; a fresh `schema.sql` and a file migrated up from v1 and from v3 have identical table and column lists, compared by test); a version 3 file migrates to 4; running the step twice changes nothing; an older clark refuses the newer file; the safety copy exists and opens.

## Writers (all in `store.py`, one Undo step each, as the other tables)
- `add_person`, `edit_person`: through the existing `write_item` path, so they land in `applies`, `change_log` and `item_events`. Email is checked (below). Because `people` has no private column, nothing private reaches `change_log` or `item_events`. Emails do: `change_log`'s before and after columns would hold an email, so they are written with the email field replaced by "changed" (as the history lines already do); a test reads both tables and the History sheet after an email edit and finds no address.
- `propose_person_change`, `accept_person_change`, `reject_person_change`: a change from someone other than the owner is staged and applied only on accept (see "People changes from someone else").
- `rename`: the person row plus the owner text of every **live** row that points at the person, one step. See "Where people changes are made and undone".
- `merge(from, into)`: one step. Repoints the owner text and `owner_id` of live rows, moves the source's aliases (and its name, as an alias) onto the target, the target's email wins on a clash, **clears the source's email before archiving it** (the unique index would refuse otherwise), then archives the source and records the mapping (below).
- `archive` and `restore`: the only way a person leaves the lists (MEDIUM 4, below).
- Import: rows pasted from Excel or CSV go through the same checks as a save, dedupe on email then on name or alias, and are one import step. A refused row is named ("row 7: the email has a space"); the other rows still apply only if the owner confirms the preview.

## People are archived, never deleted (MEDIUM 4; FR-43c)
There is no `delete` for a person. **Archive** and **restore** are the two ways (consistent with #126). A hard removal exists only as the Undo of a person created in the same step (the decided rule for creations). `merge` archives the source, the same call. `people` takes a person-specific `archived` column (above) and is listed among #126's archivable kinds; #126 lands first, so the order is #126, #120, then #115.

What archive means:
- An archived person stays as the owner text on old items; nothing is rewritten and the history keeps the name at the time.
- Archived people are hidden from the owner pickers, the type-ahead and **Not on the people list yet**, and are not matched by new saves (a name that matches only an archived person keeps its text and sets no `owner_id`; the prompt is: "Sam Reed is archived. Restore Sam Reed and use this name?" with the replies **Restore Sam Reed** and **Keep the name only**).
- They are shown on the People list under **Archived**, with a **Restore** button. Restore is one Undoable step and also puts back the email if it is still free (if not, it says: "Sam Reed is restored without an email: a.b@x.example now belongs to Sam Reid. Add a new email on the People list." and restores without it).
- Items already pointing at an archived person keep `owner_id`; an item's owner field shows the text.

## History lines (FR-43a: who, how, when)
Every people step is a line in the history (`item_events`), in this form: who made it (the user's full name), what was done, where, and the date and time (DD-MM-YYYY, 24-hour):
- Rename: "Sam Reed renamed to Sam Reid. Made by Owen Example, on the People list, 29-10-2026 at 14:05. 14 items in 3 projects now show Sam Reid."
- Merge: "Sam Reed merged into Sam Reid. Made by Owen Example, on the People list, 29-10-2026 at 14:10. 14 items now show Sam Reid; 2 aliases moved."
- Archive: "Sam Reed archived. Made by Owen Example, on the People list, 29-10-2026 at 14:12. Old items keep the name."
- Restore: "Sam Reed restored. Made by Owen Example, on the People list, 29-10-2026 at 14:20."
- Undo: "Rename of Sam Reed undone. Made by Owen Example, on the People list, 29-10-2026 at 14:30."
On an item whose owner text a rename or merge changed, the item's own history gets one line: "Owner changed from Sam Reed to Sam Reid because the person was renamed. Made by Owen Example, on the People list, 29-10-2026 at 14:05." (for a merge: "…because Sam Reed was merged into Sam Reid."). An item left alone because it was archived gets no line.

## Where people changes are made and undone (MEDIUM 3)
`changes.py` (`UNDOABLE`, `_row_is_ours`) lets an Undo reverse only steps whose rows belong to one project. A rename or merge touches owner text in several projects, so no project's Undo accepts it, and it must not run on a project-scoped route. So:
- People changes (add, edit, rename, merge, archive, restore, import, Match existing items to people) are made on **portfolio-level routes** (`/api/people/...`), not under a project, and they do not use `_row_is_ours` (which is project-scoped); a separate portfolio check (`_people_step_is_ours`) reads `people_steps` and the `later touched` rule below. A project route never writes `people_steps`.
- Each is **one step**, and a step has its own portfolio-level **Undo** on the People list ("Undo last people change"). A project's own Undo never offers a people step; a work-item step made in a project is undone there as today.
- **What Undo does.** Undo of a rename restores the person's name **and** `owner_id` and owner text on every row that step touched, everywhere, in one go. Undo of a merge restores the source person (name, email, aliases, not archived), the target's earlier aliases and email, and the owner text and `owner_id` of every row the step repointed. **Where the step is kept (second read, MEDIUM 3).** A new table, `people_steps(id INTEGER PRIMARY KEY, kind TEXT NOT NULL, person_id TEXT, made_by TEXT NOT NULL, made_at TEXT NOT NULL, undone INTEGER NOT NULL DEFAULT 0, before_json TEXT NOT NULL, after_json TEXT NOT NULL)`: the exact rows (the person, the owner text and `owner_id` of every row touched, with the earlier values) as JSON. It has its own counter (the integer key), not `next_id`, and it is created in the migration step and covered by the schema test. Undo puts back values, never recomputes them. `before_json` and `after_json` hold names and ids, and for a merge the source's email under the key `email_internal` (this is the home of the email an Undo needs: there is no "history row" for it, and `change_log` never holds an address). The People sheet, the History sheet and every history line ignore `email_internal`, and `people_for_copy` blanks it in a copy if the owner's answer to question 5 is ever no (it is yes). **Merge Undo and the unique index.** A merge clears the source's email before archiving it, and the target keeps its own; nobody else receives the source's email, so nothing can clash at that point. Undo runs in one transaction in this order: (1) the later-touch check; (2) if a different live person now holds `email_internal`, Undo is refused and names that person ("Can't undo the merge: a.b@x.example now belongs to Sam Reid. Change that email first."); (3) the source is restored with its email, then the target's aliases and the repointed rows. Because the check runs first, the order cannot deadlock.
- **Order.** A people step can be undone only while nothing later has touched the same person or rows; otherwise Undo is refused in plain words and names the later step: "Can't undo the rename of Sam Reed: the person was changed again afterwards. Undo that change first." A merge records the mapping (source id to target id, and the rows moved) so an older step on the source (an edit made before the merge) is refused with "Sam Reed was merged into Sam Reid. Undo the merge first." rather than writing to an archived person.
- **A project's Undo and a people step.** If a project edit wrote the owner text that a later rename changed, the project's Undo restores only that item's own fields; if its text now differs from what that step wrote, the Undo says "The owner was renamed after this change. Undo the rename first." and changes nothing.
- The toast after a rename or merge says what happened and how many rows: "Renamed to Sam Reid on 14 items in 3 projects. Undo." Counts include only live rows. The toast after an Undo says "Undone: Sam Reid is Sam Reed again on 14 items in 3 projects." An owner text changed by a rename is put back with it.
- **Archived projects and archived rows (first review, MEDIUM 2).** `_project_exists` refuses writes to an archived project and #126 makes archived rows read-only. A rename or merge updates **live rows only** and leaves archived rows' text as it was; the history shows the name at the time. The step's toast counts live rows and, when there are archived ones, adds "(and left 6 archived items as they were)". Test: a person who owns an item in an archived project is renamed; the live rows change, the archived one does not, and the step is one Undo.

## Rules and checks
- **Email (MEDIUM 1).** One strict single-address rule, in `store.py`, **shared with the Draft email builder (#50)**, which takes its To line and `mailto:` link from this table and must call the same function, not its own check. The rule: the value is trimmed then lower-cased; **exactly one address**; no space, `,` `;` `<` `>` `(` `)` `[` `]` `"` `'` `\` `?` `#` `%` or backtick; no control character and no invisible or bidirectional-control character (including zero-width and the bidi marks); exactly one `@`; a non-empty local part (at most 64 characters); a domain that has a dot, no empty label, no leading or trailing dot or hyphen on a label; the whole address at most 254 characters. `a,b@x.example`, `a@x.example;b@x.example`, `Sam <a@x.example>` and `a@x` are all refused. Blank is allowed (that is what Needs details is for). A duplicate is refused with the existing person named. A pasted CSV or Excel row goes through the same check and a refused email says which row. Tests: each of the above refused; a Draft email test that a person with a stored address can never produce a To line with two recipients.
- A group (`kind = 'group'`) may own items (a team owns the action), but is never counted as a person. Agreed (a reviewer LOW 3; the lead's earlier lean to "people only, groups later" is dropped by the Head's agreement; to be confirmed in the owner's question 2).
- No real names in tests, fixtures or demo data (RULES); use the fictional demo people.

## No VIP column (a reviewer's read of 0a57bf17, HIGH and MEDIUM 3)
**Decision of this note: there is no VIP column, and no private mark of any kind, in the `people` table or anywhere else in clark v0.5.** #115's ask has no such column and ARCHITECTURE.md leaves the VIP check out. A private flag in a table that is copied, shared and written to `change_log` is the risk: "visible to the owner only" means nothing on a shared page, and a generic field diff copies every column into `change_log` and `item_events`, which feed the Excel History sheet. The safest answer that also settles a reviewer's earlier HIGH is to have nothing to leak.
- If the owner wants a VIP mark in clark, it is a separate decision (question 7). The recommended shape, if it ever returns: the owner's own local setting, never a column in `people`, never in the database that is copied, shared or exported; or a table of its own (`people_private`) that `people_for_copy`, the share, the safety copy, publish, `data_for` and `change_log` never read. It would never be labelled, listed or counted in any export, history line, share, publish, toast, report, draft or message.
- The leak guards below stay in the test list as they are, so the surfaces are already guarded if the mark ever returns. Each is one assertion, run with a planted marker row (a person named "Sam Reed" with `organisation = 'PLANTED-ORG'` and a test-only side value `PLANTED-VIP`, written the way a future mark would be, into a throwaway private table the test creates):
  1. **`change_log` and `item_events`:** an edit that changes only the private value leaves no new row in either table, and an edit of other fields never has the marker in a before or after column. A People sheet and History sheet built afterwards hold no marker.
  2. **The schema:** `people` has no column named `vip` or any column not in the table above (a column-list test, so one cannot be added by accident).
  3. **Cover:** the Cover page and its data hold no marker.
  4. **Client-leak scan inputs:** the text the client-leak scan reads (`publish_inputs`) holds no marker and no email.
  5. **Demo data:** no demo person has a private mark; a test reads the demo seed and finds no marker column or `vip=1` row.
  6. **Debug log:** run an edit, an import and an Undo with logging on at the most detailed level; the log file holds no marker, no email and no organisation.
  7. **Search:** a search for the marker text, and for an email, returns nothing from `people`.
  8. **Draft email builder:** a draft for a person with a stored address holds the address only in the To line, never the marker, and no organisation.
  9. **ask clark and the AI menus:** the text sent to the model (built by the same functions that build the prompt) holds no marker, no email and no `people_steps` JSON.
  10. **`data_for` and `/api/data`:** the JSON the page can read holds no marker; `data_for` strips any private field on every route the page, a published file or a client copy can read, and `/api/data` for a client copy holds no `people` key.
  11. **Publish, client copy, share, safety copy, toasts and error messages:** none holds the marker (the planted test from the earlier revision, kept).

## Personal data stays in (MEDIUM 5 of the first review; LOW 2)
`people` holds email addresses.
- `people`, `email` and `owner_id` are in **no** publish whitelist (`PUBLISH_FIELDS`); `owner_id`, `email`, `organisation` and `people` are added to `NEVER_PUBLISH`; `publish_inputs` and `publish.select` never read the table, and are untouched. A published file and the client copy hold the owner's name as typed and no email, organisation or id. Test: plant an email, an organisation and an `owner_id` and find none of them anywhere in a publish or the client file.
- The People sheet is in the **internal** Excel export only. It passes every cell through `escape_text` (a name of `=HYPERLINK(...)` is text) and has the same row limits as the other sheets. A People sheet is never in a client copy.
- People changes from someone other than the owner are allowed (the owner's answer to question 3, yes), but only as staged changes the owner accepts or rejects; see "People changes from someone else". An owner name in a teammate's file still goes through the resolver and sets `owner_id` for an existing person, nothing more.
- The safety copies and the team share carry the whole database, so they carry the people table, emails included. The owner answered yes (question 5, 29-10-2026). If that ever changes the answer, `people.email` is blanked in a safety copy and in the share, at `store.people_for_copy` (the one blanking point), and the restore text says: "Email addresses are not kept in safety copies. Add them again on the People list." Test (both answers): plant an email, make a share and a safety copy; with yes it is there, with no it is blank.

## People changes from someone else (the owner's answer to question 3, yes, 29-10-2026)
A people change that does not come from the owner is **staged, not applied**. Nothing changes the list before the owner accepts it. Until #61 and #62 exist there is no teammate file to carry such a change, so in practice the owner is the only one who changes the list; the store, route and page are built now, and a test stands in for the teammate.
- **Where a staged change lives.** A new table `people_staged(id INTEGER PRIMARY KEY, kind TEXT NOT NULL, person_id TEXT, proposed_by TEXT NOT NULL, proposed_at TEXT NOT NULL, how TEXT NOT NULL, before_json TEXT NOT NULL, after_json TEXT NOT NULL, status TEXT NOT NULL DEFAULT 'staged' CHECK IN ('staged','accepted','rejected'), decided_by TEXT, decided_at TEXT, decided_how TEXT, step_id INTEGER REFERENCES people_steps(id))`. It is created in the migration step and covered by the schema test. A staged change has no effect on any `people` row, `owner_id` or owner text.
- **Accept** applies it as one ordinary people step (a row in `people_steps` with `made_by` the owner), through the same writers and checks as a save (email rule, limits, resolver), and records `decided_by`, `decided_at`, `decided_how` ("on the People list") and the `step_id`. If the change no longer fits (the person was merged or archived meanwhile, or the email is now taken) the accept is refused in plain words and the change stays staged. **Reject** records the same fields and changes nothing else.
- **Undo of an accepted change** is the ordinary "Undo last people change" on the step the accept made; the order rules above apply. The staged line then reads "Accepted and undone".
- **Allowed fields in a changes file.** #61's list of allowed fields must name people when #61 is picked up; this note adds nothing to #61 and the people route reads no teammate file until then.
- **History** (FR-43a). One line when it is proposed, one when it is decided: "Sam Reed's role: change to Lead proposed by Jo Example, in a teammate's file, 29-10-2026 at 15:02." then "Change to Sam Reed's role accepted by Owen Example, on the People list, 29-10-2026 at 15:20. Proposed by Jo Example, 29-10-2026 at 15:02." (or "rejected by"). The accepted line carries who proposed, who accepted, how and when; an Undo adds "Change to Sam Reed's role undone. Made by Owen Example, on the People list, 29-10-2026 at 15:30."
- **Plain words on screen.** A section on the People list, **Changes waiting for you**, one line each: "Jo Example suggests: Sam Reed's role from Analyst to Lead. Proposed 29-10-2026 at 15:02." with the buttons **Accept** and **Reject** (and **Accept all** only when there is more than one; it still records each change). Empty state: "No changes are waiting." A count badge on the People list tab when any wait. Refused accept: "Can't accept this: Sam Reed was merged into Sam Reid after it was proposed. Reject it, or ask Jo Example to propose it again." The proposer sees no people message (as before).
